# ADR-003: Domain Events パターンの採用

## ステータス
承認済み

## コンテキスト
認証ドメインで重要なビジネスイベント（認証成功、トークン更新、ログアウトなど）が発生した際、他のコンポーネント（UI、ログ、監視など）に通知する必要がありました。

ドメイン層とアプリケーション層の疎結合を実現し、将来の拡張性を確保する必要があります。

## 決定
Domain Events パターンを採用し、重要なビジネスイベントをイベントとして発行します：

- **ドメイン層**: Domain Eventsを定義（`UserAuthenticated`, `TokenRefreshed`, `AuthenticationFailed`, `UserLoggedOut`, `CalendarInitialized`）
- **アプリケーション層**: EventHandlerでイベントを処理し、UI更新やログ記録を実行

## 結果

### ポジティブ
- **疎結合**: ドメイン層とアプリケーション層の疎結合を実現
- **拡張性**: 新しいイベントハンドラーを追加するだけで機能を拡張可能
- **テスト容易性**: イベントの発行をテスト可能
- **監視とログ**: イベントをログや監視システムに送信可能
- **将来の拡張**: イベント駆動アーキテクチャへの移行が容易

### ネガティブ
- **複雑性の増加**: イベントの発行と処理により、コードの複雑性が増加
- **デバッグの困難さ**: イベントの流れを追跡するのが困難な場合がある
- **イベントの順序**: イベントの処理順序を保証する必要がある場合がある

### 検討した代替案

#### 代替案1: 直接的な呼び出し
- **説明**: ドメイン層から直接アプリケーション層のメソッドを呼び出す
- **却下理由**: ドメイン層がアプリケーション層に依存、疎結合が実現できない

#### 代替案2: Observer パターン
- **説明**: Observer パターンを使用してイベントを通知
- **却下理由**: Domain Events パターンの方が、ドメイン駆動設計の原則に適合

#### 代替案3: イベントなし
- **説明**: イベントを発行せず、直接的な処理のみ
- **却下理由**: 拡張性が低い、将来の変更が困難
