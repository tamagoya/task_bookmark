# ADR-026: パフォーマンス最適化の統合方法

## コンテキスト

Unit 6では、既存のUnit（1-5）にパフォーマンス最適化機能を統合する必要があります。特に、以下の操作で最適化が必要です：

- タブ情報の取得: 500ms以内（Unit 2）
- カレンダーイベントの保存: 2秒以内（Unit 3）
- 保存済み仕事の一覧取得: 3秒以内（Unit 3）
- タブの復元（10個）: 5秒以内（Unit 4）

パフォーマンス最適化を既存のUnitに統合する際、以下の選択肢があります：

1. **Decorator パターン**: 既存のサービスをラップしてパフォーマンス監視とキャッシュを追加
2. **Dependency Injection**: 既存のサービスに`PerformanceInterceptor`と`CacheDecorator`を注入
3. **Aspect-Oriented Programming (AOP)**: 横断的関心事を分離（ただし、TypeScriptでは完全なAOPフレームワークが限定的）
4. **既存サービスの直接修正**: 既存のサービスメソッド内でパフォーマンス最適化を実装

## 決定

**Decorator パターンとDependency Injectionを組み合わせた実装**を選択します。

具体的には：
- `PerformanceInterceptor`と`CacheDecorator`を既存のサービスに注入
- 各サービスのメソッド呼び出し時に`PerformanceInterceptor.intercept()`と`CacheDecorator.withCache()`を使用
- 既存のサービスメソッドは変更せず、ラップするだけでパフォーマンス最適化を追加
- `PerformanceOptimizationService`で最適化戦略（キャッシュ戦略、バッチサイズ）を決定

## 結果

### ポジティブ

- **既存コードへの影響が最小限**: 既存のサービスメソッドを変更せず、ラップするだけでパフォーマンス最適化を追加できる
- **横断的関心事の分離**: パフォーマンス最適化のロジックを一箇所に集約できる
- **テスト容易性**: `PerformanceInterceptor`と`CacheDecorator`をモック化してテストできる
- **柔軟性**: 各サービスで個別にパフォーマンス最適化を有効/無効にできる
- **拡張性**: 将来的に他の最適化機能（バッチ処理、並列処理など）を追加しやすい

### ネガティブ

- **コードの複雑性**: 各サービスのメソッド呼び出し時に`PerformanceInterceptor`と`CacheDecorator`を使用する必要がある
- **依存関係の増加**: 既存のサービスに新しい依存関係（`PerformanceInterceptor`、`CacheDecorator`）を追加する必要がある
- **パフォーマンスオーバーヘッド**: デコレーターのラップによるオーバーヘッドが発生する（ただし、非同期処理で最小化）

### 検討した代替案

- **Aspect-Oriented Programming (AOP)**: TypeScriptでは完全なAOPフレームワークが限定的で、実装が複雑になる。また、Chrome Extension環境では追加のライブラリ依存が問題になる可能性がある。
- **既存サービスの直接修正**: 既存のサービスメソッド内でパフォーマンス最適化を実装する方法。コードの重複が発生し、保守性が低下する。また、既存のコードを変更する必要があり、リスクが高い。
- **Middleware パターン**: ミドルウェアパターンを使用してパフォーマンス最適化を実装する方法。ただし、Chrome Extension環境では複雑で、実装コストが高い。
