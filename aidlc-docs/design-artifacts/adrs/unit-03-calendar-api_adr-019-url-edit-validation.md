# ADR-019: URL編集のバリデーション戦略

## ステータス
承認済み

## コンテキスト
Bolt 8（URL編集機能）では、ユーザーが入力したURLやタブリストを編集する際に、データの整合性を保つために適切なバリデーションが必要です。

バリデーションは、以下のレベルで実行する必要があります：
1. **ドメイン層**: ビジネスルールに基づくバリデーション（タブリストの最小要件、インデックスの連続性など）
2. **アプリケーション層**: ユースケースに基づくバリデーション（イベントIDの存在確認など）
3. **UI層**: ユーザー入力の即座のフィードバック（URL形式の検証など）

## 決定
URL編集のバリデーション戦略として、以下のアプローチを採用します：

1. **ドメイン層でのバリデーション**: `WorkState`エンティティのメソッドでバリデーションを実行
   - `validateTabList()`: タブリスト全体のバリデーション
   - 各編集メソッド（`updateTabs`, `addTab`, `removeTab`, `reorderTabs`）内でバリデーションを実行

2. **ValidationError Value Object**: バリデーションエラーを`ValidationError` Value Objectとして表現
   - エラーフィールド、エラーコード、エラーメッセージ、深刻度を含む
   - 複数のエラーを同時に返すことができる

3. **段階的なバリデーション**: 
   - まず、基本的なバリデーション（空配列チェック、インデックスの範囲チェック）を実行
   - 次に、詳細なバリデーション（TabInfoの有効性、インデックスの連続性）を実行

4. **UI層での事前バリデーション**: ユーザー入力の即座のフィードバック（オプション、将来の拡張）

## 結果

### ポジティブ
- **データ整合性**: ドメイン層でのバリデーションにより、無効な状態を防ぐ
- **再利用性**: `ValidationError` Value Objectは、既存の破損データ処理でも使用されている
- **テスト容易性**: ドメイン層でのバリデーションは、テストが容易
- **エラー情報の詳細性**: 複数のエラーを同時に返すことができる

### ネガティブ
- **パフォーマンス**: 大量のタブ（100個以上）を編集する場合、バリデーションに時間がかかる可能性（ただし、通常の使用では問題にならない）
- **UI層との重複**: UI層でもURL形式の検証を行う場合、バリデーションロジックが重複する可能性

### 検討した代替案

#### 代替案1: アプリケーション層でのみバリデーション
- **説明**: ドメイン層ではなく、アプリケーション層でのみバリデーションを実行
- **却下理由**: ドメイン層でのバリデーションにより、ビジネスルールが明確になる、テスト容易性が高い

#### 代替案2: 外部バリデーションライブラリの使用
- **説明**: ZodやYupなどのバリデーションライブラリを使用
- **却下理由**: 既存のコードベースでは`ValidationError` Value Objectを使用している、一貫性を保つため

#### 代替案3: 遅延バリデーション
- **説明**: 編集操作時にバリデーションを実行せず、保存時にのみバリデーションを実行
- **却下理由**: ユーザーエクスペリエンスが悪い、早期のエラー検出ができない

## 実装上の注意事項

1. **バリデーションの順序**:
   - まず、基本的なバリデーション（空配列チェック、インデックスの範囲チェック）を実行
   - 次に、詳細なバリデーション（TabInfoの有効性、インデックスの連続性）を実行
   - エラーが発生した場合、すべてのエラーを収集して返す

2. **エラーメッセージ**:
   - ユーザーフレンドリーな日本語メッセージを提供
   - エラーコードとエラーメッセージの両方を含む

3. **パフォーマンス**:
   - 大量のタブ（100個以上）を編集する場合でも、バリデーションが2秒以内に完了することを確認
   - 必要に応じて、バリデーションを最適化
