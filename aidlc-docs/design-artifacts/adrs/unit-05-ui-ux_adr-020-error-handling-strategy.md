# ADR-020: エラーハンドリング戦略の統一化

## ステータス
提案

## コンテキスト

Bolt 9では、エラーハンドリングを統一化し、ユーザーフレンドリーなエラーメッセージを提供する必要があります。現在、エラーハンドリングは各Unitで個別に実装されており、以下の問題があります：

1. **エラーメッセージの不統一**: 各Unitで異なる形式のエラーメッセージが表示される
2. **エラー分類の欠如**: エラーの種類や重要度が明確に分類されていない
3. **リトライ処理の不統一**: リトライ可能なエラーと不可能なエラーの判定が一貫していない
4. **技術的なエラーメッセージ**: ユーザーが理解できない技術的なエラーメッセージが表示される場合がある

## 決定

**エラーハンドリング戦略を統一化**し、ドメイン層でエラー分類とメッセージ生成を行う。

### 実装アプローチ

1. **ドメイン層でのエラー分類**: `ErrorCode`、`ErrorCategory`、`ErrorSeverity` Value Objectsを定義
2. **エラーハンドリングサービス**: `ErrorHandlingService`（Domain Service）でエラー分類とメッセージ生成を統一
3. **ユーザーフレンドリーなメッセージ**: `ErrorMessage` Value Objectで技術的な詳細を隠し、ユーザーが理解できる日本語メッセージを生成
4. **Domain Events**: `ErrorOccurred`、`RetryRequested`、`RetrySucceeded`、`RetryFailed`イベントを発行

### エラー分類ルール

- **認証エラー**: `AUTH_FAILED`, `TOKEN_EXPIRED` → `AUTHENTICATION`カテゴリ、`ERROR`重要度
- **ネットワークエラー**: `NETWORK_ERROR`, `TIMEOUT`, `OFFLINE` → `NETWORK`カテゴリ、`ERROR`重要度（リトライ可能）
- **APIエラー**: `RATE_LIMIT_EXCEEDED`, `API_ERROR` → `API`カテゴリ、`WARNING`重要度（リトライ可能）
- **バリデーションエラー**: `VALIDATION_ERROR`, `INVALID_INPUT` → `VALIDATION`カテゴリ、`WARNING`重要度（リトライ不可能）
- **データエラー**: `DATA_CORRUPTED` → `DATA`カテゴリ、`CRITICAL`重要度（リトライ不可能）

## 結果

### ポジティブ

- **一貫性**: すべてのエラーが統一された方法で処理される
- **ユーザー体験**: ユーザーフレンドリーなメッセージにより、エラーを理解しやすくなる
- **保守性**: エラーハンドリングロジックが一箇所に集約され、保守が容易になる
- **拡張性**: 新しいエラーコードを追加する際の手順が明確になる
- **テスト容易性**: エラーハンドリングロジックを独立してテストできる

### ネガティブ

- **実装コスト**: 既存のエラーハンドリングコードをリファクタリングする必要がある
- **学習コスト**: 新しいエラーハンドリングアーキテクチャを理解する必要がある
- **パフォーマンス**: エラー分類とメッセージ生成のオーバーヘッドが発生する（ただし、エラー発生時のみ）

### 検討した代替案

#### 代替案1: 各Unitで個別にエラーハンドリングを実装
- **説明**: 現在のアプローチを維持し、各Unitで個別にエラーハンドリングを実装
- **Pros**: 実装が簡単、既存コードの変更が少ない
- **Cons**: エラーメッセージの不統一、保守性の低下、コードの重複
- **却下理由**: ユーザー体験と保守性の観点から不適切

#### 代替案2: インフラストラクチャ層でエラーハンドリングを実装
- **説明**: エラーハンドリングロジックをインフラストラクチャ層に配置
- **Pros**: ドメイン層の複雑性を減らせる
- **Cons**: ビジネスルール（エラー分類、メッセージ生成）がインフラストラクチャ層に混在する
- **却下理由**: DDDの原則に反し、ビジネスルールはドメイン層に配置すべき

#### 代替案3: アプリケーション層でエラーハンドリングを実装
- **説明**: エラーハンドリングロジックをアプリケーション層に配置
- **Pros**: ドメイン層の複雑性を減らせる
- **Cons**: エラー分類とメッセージ生成のロジックが複数のアプリケーションサービスに分散する可能性がある
- **却下理由**: エラーハンドリングは横断的関心事であり、Domain Serviceとして実装する方が適切
