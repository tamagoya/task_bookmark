# ADR-002: Repository パターンの採用

## ステータス
承認済み

## コンテキスト
認証状態の永続化を実装する際、Chrome Storage APIの詳細をドメイン層から隠蔽し、テスト容易性を確保する必要がありました。

将来的に永続化方法が変更される可能性（例: サーバーサイドへの移行）も考慮する必要があります。

## 決定
Repository パターンを採用し、永続化の抽象化を実現します：

- **ドメイン層**: `AuthRepository`インターフェースを定義
- **インフラストラクチャ層**: `AuthRepositoryImpl`でChrome Storage APIを使用して実装

## 結果

### ポジティブ
- **永続化の抽象化**: ドメイン層が永続化の詳細を知る必要がない
- **テスト容易性**: モックリポジトリを使用してドメイン層をテスト可能
- **将来の拡張性**: 永続化方法を変更しても、ドメイン層への影響が最小限
- **依存関係の逆転**: ドメイン層がインフラストラクチャ層に依存しない

### ネガティブ
- **コード量の増加**: インターフェースと実装の分離により、コード量が増加
- **オーバーエンジニアリングのリスク**: シンプルな永続化に対して過剰な可能性

### 検討した代替案

#### 代替案1: 直接的な永続化
- **説明**: ドメイン層から直接Chrome Storage APIを呼び出す
- **却下理由**: テスト困難、ドメイン層がインフラストラクチャに依存、将来の変更が困難

#### 代替案2: Active Record パターン
- **説明**: エンティティが自身の永続化を担当
- **却下理由**: ドメイン層がインフラストラクチャに依存、単一責任の原則に違反
