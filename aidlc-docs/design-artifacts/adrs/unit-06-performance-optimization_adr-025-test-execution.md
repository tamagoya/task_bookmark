# ADR-025: テスト実行アーキテクチャ

## コンテキスト

Unit 6では、テストカバレッジ80%以上（NFR要件）を達成するために、テスト実行とカバレッジ計算のアーキテクチャを設計する必要があります。

現在のプロジェクトでは、Jestを使用してテストを実行しています。テスト実行アーキテクチャを実装する際、以下の選択肢があります：

1. **Jestを直接使用**: 既存のJestの機能をそのまま使用し、テスト実行とカバレッジ計算を実行
2. **Test Runner パターン**: テスト実行を抽象化し、`TestRunner`インターフェースでラップ
3. **Test Execution Service**: アプリケーション層に`TestExecutionService`を作成し、テスト実行を管理
4. **外部ツール**: 外部のテスト実行ツール（例: Mocha、Jasmine）を使用

## 決定

**Test Runner パターンとTest Execution Serviceを組み合わせた実装**を選択します。

具体的には：
- `TestRunner`インターフェースを定義し、`JestTestRunner`で実装
- アプリケーション層に`TestExecutionService`を作成し、テスト実行を管理
- テスト結果は`TestResult` Value Objectで表現
- テストカバレッジは`TestCoverageService`で計算し、`CoverageCalculator`インターフェースで抽象化
- Jestの既存機能（並列実行、カバレッジ計算）を活用

## 結果

### ポジティブ

- **抽象化**: テスト実行を抽象化することで、将来的に他のテストフレームワークに切り替えやすくなる
- **ドメインモデルとの統合**: テスト結果とカバレッジをドメインモデル（`TestResult`、`TestCoverage`）で表現
- **既存ツールの活用**: Jestの既存機能（並列実行、カバレッジ計算）を活用できる
- **テスト容易性**: `TestRunner`をモック化してテストできる
- **拡張性**: 将来的に他のテストタイプ（E2Eテストなど）を追加しやすい

### ネガティブ

- **抽象化のオーバーヘッド**: インターフェースと実装クラスを追加することで、コードの複雑性が増加
- **Jestへの依存**: 実装はJestに依存するため、完全な抽象化は難しい
- **実装の複雑性**: `TestExecutionService`と`TestCoverageService`の実装が複雑になる可能性がある

### 検討した代替案

- **Jestを直接使用**: 既存のJestの機能をそのまま使用する方法。シンプルだが、ドメインモデルとの統合が困難で、将来的な拡張性が低い。
- **外部ツール**: 外部のテスト実行ツール（例: Mocha、Jasmine）を使用する方法。ただし、既存のJestの設定とテストコードを書き換える必要があり、コストが高い。
- **Test Execution Serviceのみ**: `TestExecutionService`のみを作成し、`TestRunner`インターフェースを省略する方法。ただし、抽象化が不十分で、将来的な拡張性が低い。
