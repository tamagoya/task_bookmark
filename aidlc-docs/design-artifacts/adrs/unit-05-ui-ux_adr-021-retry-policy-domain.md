# ADR-021: リトライポリシーのドメイン層定義

## ステータス
提案

## コンテキスト

Bolt 9では、リトライ処理を統一化し、どのエラーがリトライ可能か、どのような戦略でリトライするかを明確にする必要があります。現在、`RetryHandler`がインフラストラクチャ層に存在しますが、リトライポリシー（どのエラーがリトライ可能か、最大リトライ回数、バックオフ戦略など）は固定値として実装されています。

以下の問題があります：

1. **リトライポリシーのハードコード**: リトライポリシーがインフラストラクチャ層にハードコードされている
2. **ビジネスルールの混在**: リトライ可能なエラーの判定がビジネスルールであるにもかかわらず、インフラストラクチャ層に実装されている
3. **拡張性の欠如**: 異なるエラーに対して異なるリトライポリシーを適用することが困難

## 決定

**リトライポリシーをドメイン層で定義**し、インフラストラクチャ層の`RetryHandler`はドメイン層の`RetryPolicy`を使用する。

### 実装アプローチ

1. **ドメイン層でのリトライポリシー定義**: `RetryPolicy` Value Objectを定義
   - `maxRetries`: 最大リトライ回数
   - `baseDelayMs`: ベース遅延時間
   - `backoffStrategy`: バックオフ戦略（LINEAR, EXPONENTIAL, FIXED）
   - `retryableErrorCodes`: リトライ可能なエラーコードのリスト

2. **既存のRetryHandlerの拡張**: インフラストラクチャ層の`RetryHandler`を拡張し、`RetryPolicy`を受け取るように変更

3. **リトライ可能性の判定**: `ErrorHandlingService.isRetryable()`メソッドで、エラーコードとリトライポリシーからリトライ可能かどうかを判定

### リトライルール

- **リトライ可能なエラー**: ネットワークエラー、APIエラー（レート制限を除く）
- **リトライ不可能なエラー**: 認証エラー（再認証が必要）、バリデーションエラー、データエラー
- **レート制限エラー**: リトライ可能だが、`Retry-After`ヘッダーに基づいて待機時間を調整

## 結果

### ポジティブ

- **ビジネスルールの明確化**: リトライポリシーがドメイン層で定義され、ビジネスルールとして明確になる
- **柔軟性**: 異なるエラーに対して異なるリトライポリシーを適用できる
- **テスト容易性**: リトライポリシーを独立してテストできる
- **保守性**: リトライポリシーの変更が容易になる

### ネガティブ

- **実装コスト**: 既存の`RetryHandler`をリファクタリングする必要がある
- **複雑性**: ドメイン層に新しいValue Objectが追加される

### 検討した代替案

#### 代替案1: リトライポリシーをインフラストラクチャ層に保持
- **説明**: 現在のアプローチを維持し、リトライポリシーをインフラストラクチャ層に保持
- **Pros**: 実装が簡単、既存コードの変更が少ない
- **Cons**: ビジネスルールがインフラストラクチャ層に混在する、拡張性が低い
- **却下理由**: DDDの原則に反し、ビジネスルールはドメイン層に配置すべき

#### 代替案2: アプリケーション層でリトライポリシーを定義
- **説明**: リトライポリシーをアプリケーション層で定義
- **Pros**: ドメイン層の複雑性を減らせる
- **Cons**: リトライポリシーが複数のアプリケーションサービスに分散する可能性がある
- **却下理由**: リトライポリシーは横断的関心事であり、ドメイン層で定義する方が適切
