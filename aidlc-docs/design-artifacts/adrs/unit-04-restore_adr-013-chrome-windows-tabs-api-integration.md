# ADR-013: Chrome Windows APIとChrome Tabs APIの統合パターン

## ステータス
承認済み

## コンテキスト
Unit 4（状態復元機能）では、Chrome Windows APIとChrome Tabs APIを使用して、新しいウィンドウを作成し、タブを復元する必要があります。

Unit 2で既に以下のパターンが実装されています：
- Adapter パターン（ChromeTabsAdapter、ChromeWindowsAdapter）
- Service Layer パターン（TabCaptureService）
- レイヤードアーキテクチャ

Unit 4では、これらのパターンと一貫性を保ちながら、ウィンドウ作成とタブ作成機能を実装する必要があります。

## 決定
Chrome Windows APIとChrome Tabs APIの統合パターンを採用します：

1. **Adapter パターンの拡張**: `ChromeTabsAdapter`と`ChromeWindowsAdapter`を拡張
   - Unit 2で実装済みのアダプターを拡張
   - タブ作成機能（`createTab()`, `createTabs()`）を追加
   - ウィンドウ作成機能（`createWindow()`）を追加
   - 外部APIの詳細を抽象化
   - テスト容易性の向上（モック可能）

2. **Service Layer パターンの採用**: `RestoreService`と`TabRestoreManager`を実装
   - 復元処理のアプリケーションロジックを集約
   - ドメイン層とインフラストラクチャ層の調整
   - Unit 1, 2, 3のパターンと一貫性を保つ

3. **順序保証の実装**: タブを順番通りに作成（並列処理を避ける）
   - Chrome Tabs APIの`chrome.tabs.create()`を並列実行すると順序が保証されない
   - ユーザー要件: タブの順序が保持される必要がある
   - 実装: `for`ループで順番通りにタブを作成

4. **エラーハンドリング戦略**: 部分的な復元を許容
   - 無効なURLやネットワークエラーが発生したタブはスキップ
   - 成功したタブは開いたまま
   - 失敗したタブのリストをユーザーに表示

5. **レイヤードアーキテクチャの維持**: Unit 1, 2, 3と同じ3層構造
   - ドメイン層: Unit 3のドメインモデルを再利用
   - アプリケーション層: RestoreService、TabRestoreManager
   - インフラストラクチャ層: ChromeTabsAdapter（拡張）、ChromeWindowsAdapter（拡張）

## 結果

### ポジティブ
- **一貫性**: Unit 1, 2, 3のパターンと一貫性を保つ
- **テスト容易性**: Adapter パターンにより、ドメイン層とアプリケーション層をテスト可能
- **保守性**: 各層の責任が明確
- **拡張性**: 将来の機能追加に対応できる
- **再利用性**: Unit 2で実装済みのコンポーネント（ChromeTabsAdapter、ChromeWindowsAdapter）を拡張

### ネガティブ
- **コード量の増加**: インターフェースと実装の分離により、コード量が増加
- **パフォーマンス**: 順序保証のため並列処理を避けるため、大量タブの復元に時間がかかる可能性（ただし、段階的読み込みで軽減）

### 検討した代替案

#### 代替案1: 直接的なAPI呼び出し
- **説明**: アプリケーション層から直接Chrome Windows API、Chrome Tabs APIを呼び出す
- **却下理由**: テスト困難、ドメイン層がインフラストラクチャに依存、Unit 1, 2, 3のパターンと一貫性がない

#### 代替案2: 並列処理による高速化
- **説明**: `Promise.all()`を使用してタブを並列に作成
- **却下理由**: タブの順序が保証されない、ユーザー要件に違反

#### 代替案3: 新しいAdapter実装
- **説明**: Unit 2とは別のAdapterを実装
- **却下理由**: コードの重複、保守性の低下、一貫性の欠如

#### 代替案4: エラー時に処理を中断
- **説明**: タブ復元エラーが発生した場合、処理を中断
- **却下理由**: ユーザー体験の低下、部分的な復元ができない
