# ADR-023: パフォーマンス監視の実装方法

## コンテキスト

Unit 6では、すべてのUnit（1-5）にまたがるパフォーマンス監視機能を実装する必要があります。NFRsでは、以下のパフォーマンス要件が定義されています：

- タブ情報の取得: 500ms以内
- カレンダーイベントの保存: 2秒以内
- 保存済み仕事の一覧取得: 3秒以内
- タブの復元（10個）: 5秒以内
- メモリ使用量: 50MB以内
- CPU使用率: 5%以内（アイドル時）

パフォーマンス監視を実装する際、以下の選択肢があります：

1. **Decorator パターン**: 既存のサービスをラップしてパフォーマンス監視を追加
2. **Interceptor パターン**: メソッド呼び出しをインターセプトしてパフォーマンスメトリクスを記録
3. **Aspect-Oriented Programming (AOP)**: 横断的関心事を分離（ただし、TypeScriptでは完全なAOPフレームワークが限定的）
4. **手動計測**: 各サービスのメソッド内で手動でパフォーマンスを計測

## 決定

**Decorator パターンとInterceptor パターンを組み合わせた実装**を選択します。

具体的には：
- `PerformanceInterceptor`クラスを作成し、既存のサービスメソッドをラップ
- 各サービスのメソッド呼び出し時に`PerformanceInterceptor.intercept()`を使用
- パフォーマンスメトリクス（実行時間、メモリ使用量、CPU使用率）を非同期で記録
- パフォーマンス閾値をチェックし、超過時は`PerformanceThresholdExceeded`イベントを発行

## 結果

### ポジティブ

- **既存コードへの影響が最小限**: 既存のサービスメソッドを変更せず、ラップするだけでパフォーマンス監視を追加できる
- **横断的関心事の分離**: パフォーマンス監視のロジックを一箇所に集約できる
- **テスト容易性**: `PerformanceInterceptor`をモック化してテストできる
- **非同期処理**: メトリクス記録を非同期で実行することで、メインの操作への影響を最小化
- **拡張性**: 将来的に他の監視機能（エラー追跡、使用状況分析など）を追加しやすい

### ネガティブ

- **コードの複雑性**: 各サービスのメソッド呼び出し時に`PerformanceInterceptor`を使用する必要がある
- **オーバーヘッド**: メトリクス収集のオーバーヘッドが発生する（ただし、非同期処理で最小化）
- **Chrome Extension APIの制約**: メモリ使用量とCPU使用率の直接的な取得が制限される可能性がある

### 検討した代替案

- **Aspect-Oriented Programming (AOP)**: TypeScriptでは完全なAOPフレームワークが限定的で、実装が複雑になる。また、Chrome Extension環境では追加のライブラリ依存が問題になる可能性がある。
- **手動計測**: 各サービスのメソッド内で手動でパフォーマンスを計測する方法。コードの重複が発生し、保守性が低下する。
- **外部監視ツール**: Chrome DevToolsや外部のAPMツールを使用する方法。ただし、本拡張機能ではローカル環境での監視が要件であり、外部ツールへの依存は避けたい。
