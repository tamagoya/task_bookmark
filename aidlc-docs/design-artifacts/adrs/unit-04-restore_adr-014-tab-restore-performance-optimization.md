# ADR-014: タブ復元のパフォーマンス最適化戦略

## ステータス
承認済み

## コンテキスト
Unit 4（状態復元機能）では、パフォーマンス要件として「10個のタブを5秒以内で復元する必要がある」（NFR-001）があります。

また、大量のタブ（20個以上）を復元する場合、ブラウザのリソース使用を抑制し、ユーザー体験を向上させる必要があります。

Chrome Tabs APIの`chrome.tabs.create()`は、並列実行すると順序が保証されないため、順番通りにタブを作成する必要があります。しかし、順番通りに作成すると、大量タブの復元に時間がかかる可能性があります。

## 決定
タブ復元のパフォーマンス最適化戦略として、以下の戦略を採用します：

1. **段階的なタブ読み込み（バッチ処理）**: Strategy パターンを使用
   - **バッチサイズ**: 5個ずつ
   - **待機時間**: 各バッチの間に100ms
   - **適用条件**: タブ数が20個以上の場合
   - **理由**: ブラウザのリソース使用を抑制し、パフォーマンスを最適化

2. **順序保証**: 順番通りにタブを作成（並列処理を避ける）
   - **理由**: Chrome Tabs APIの`chrome.tabs.create()`を並列実行すると順序が保証されない
   - **実装**: `for`ループで順番通りにタブを作成
   - **トレードオフ**: パフォーマンスよりも順序保証を優先

3. **最大タブ数の制限**: 30個を超える場合は警告を表示
   - **理由**: ブラウザのリソース使用を抑制
   - **ユーザー体験**: ユーザーに確認を求める

4. **プログレス通知**: 復元中の進捗をユーザーに通知
   - **実装**: コールバック関数を使用（`onProgress?: (completed: number, total: number) => void`）
   - **理由**: 大量タブの復元中、ユーザーに進捗を表示

## 結果

### ポジティブ
- **パフォーマンス要件の達成**: 10タブを5秒以内で復元可能（順番通りに作成しても十分に高速）
- **大量タブの処理**: 20個以上のタブを段階的に読み込むことで、ブラウザのリソース使用を抑制
- **ユーザー体験**: プログレス通知により、復元中の進捗をユーザーに表示
- **順序保証**: タブの順序が保持される

### ネガティブ
- **大量タブの復元時間**: 20個以上のタブを復元する場合、段階的読み込みにより時間がかかる（例: 25タブの場合、約1.5秒）
- **順序保証のコスト**: 並列処理を避けるため、大量タブの復元に時間がかかる可能性（ただし、段階的読み込みで軽減）

### 検討した代替案

#### 代替案1: 並列処理による高速化
- **説明**: `Promise.all()`を使用してタブを並列に作成
- **却下理由**: タブの順序が保証されない、ユーザー要件に違反

#### 代替案2: 一括読み込み（段階的読み込みなし）
- **説明**: すべてのタブを一度に作成
- **却下理由**: 大量タブ（20個以上）の場合、ブラウザのリソース使用が過剰になる可能性

#### 代替案3: バッチサイズの動的調整
- **説明**: タブ数に応じてバッチサイズを動的に調整
- **却下理由**: 複雑性の増加、実装コストが高い、現時点では不要

#### 代替案4: 遅延読み込み（タブを開いた後、実際のページ読み込みを遅延）
- **説明**: タブを開いた後、実際のページ読み込みを遅延させる
- **却下理由**: 実装が複雑、ユーザー要件に含まれていない（将来の拡張で検討可能）

## パフォーマンス見積もり

### 10タブの復元
- **見積もり**: 約2-3秒（順番通りに作成）
- **要件**: 5秒以内 ✅

### 20タブの復元
- **見積もり**: 約4-5秒（段階的読み込み: 4バッチ × 1秒 + 3 × 100ms = 約4.3秒）
- **要件**: 段階的読み込みで最適化 ✅

### 30タブの復元
- **見積もり**: 約6-7秒（段階的読み込み: 6バッチ × 1秒 + 5 × 100ms = 約6.5秒）
- **要件**: 警告を表示してユーザーに確認を求める ✅
