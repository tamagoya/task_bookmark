# ADR-018: URL編集操作のトランザクション性

## ステータス
承認済み

## コンテキスト
Bolt 8（URL編集機能）では、保存済み仕事状態のタブリストを編集する機能を実装する必要があります。編集操作（追加、削除、順序変更）は、データ整合性を保つためにトランザクション的に実行される必要があります。

Google Calendar APIは、単一のイベント更新操作をサポートしていますが、複数の操作を1つのトランザクションとして実行する機能は提供していません。

## 決定
URL編集操作をトランザクション的に実行するために、以下のアプローチを採用します：

1. **楽観的ロック**: 編集操作前に既存のWorkStateを取得し、編集後に更新する
2. **単一のAPI呼び出し**: 編集操作は、1つの`updateEvent` API呼び出しで完了する
3. **ドメイン層での整合性保証**: `WorkState`エンティティのメソッド（`updateTabs`, `addTab`, `removeTab`, `reorderTabs`）で整合性を保証
4. **バリデーション**: 編集操作前に、タブリストのバリデーションを実行

## 結果

### ポジティブ
- **データ整合性**: ドメイン層での整合性保証により、無効な状態を防ぐ
- **シンプルな実装**: 単一のAPI呼び出しで完了するため、実装がシンプル
- **パフォーマンス**: 1回のAPI呼び出しで完了するため、パフォーマンスが良い
- **エラーハンドリング**: 編集操作中のエラーを1箇所で処理できる

### ネガティブ
- **同時編集の制限**: 複数のユーザーが同時に編集した場合、後勝ちになる（楽観的ロック）
- **部分的な失敗**: API呼び出しが失敗した場合、編集操作全体が失敗する（ただし、これは期待される動作）

### 検討した代替案

#### 代替案1: 悲観的ロック
- **説明**: 編集操作前にロックを取得し、編集完了まで他の操作をブロック
- **却下理由**: Chrome拡張機能の環境では、ロック機構を実装するのが困難、Google Calendar APIはロック機能を提供していない

#### 代替案2: バッチ更新API
- **説明**: 複数の編集操作を1つのバッチリクエストで送信
- **却下理由**: Google Calendar APIはバッチ更新APIを提供していない、実装が複雑になる

#### 代替案3: 操作履歴の記録
- **説明**: 各編集操作を個別に記録し、順次適用
- **却下理由**: 実装が複雑、パフォーマンスが低下、Google Calendar APIの制限により非効率

## 実装上の注意事項

1. **楽観的ロックの実装**:
   - 編集操作前に`CalendarEventRepository.findById()`で既存のWorkStateを取得
   - 編集操作後、`CalendarEventRepository.update()`で更新
   - 更新時に、既存のデータが変更されていないことを確認（オプション、将来の拡張）

2. **エラーハンドリング**:
   - API呼び出しが失敗した場合、編集操作全体をロールバック（新しいWorkStateMetadataは作成されない）
   - ユーザーにエラーメッセージを表示し、再試行を促す

3. **バリデーション**:
   - 編集操作前に、`WorkState.validateTabList()`でバリデーションを実行
   - バリデーションエラーが発生した場合、API呼び出しを行わずにエラーを返す
