# ADR-022: アクセシビリティ要件のドメイン層定義

## ステータス
提案

## コンテキスト

Bolt 9では、アクセシビリティ要件（ARIAラベル、キーボードショートカット）を実装する必要があります。アクセシビリティ要件はUI層の関心事ですが、一貫性を保つためにドメイン層で定義する必要があります。

以下の問題があります：

1. **アクセシビリティ要件の分散**: ARIAラベルやキーボードショートカットがUI層に直接記述され、一貫性が保たれない
2. **ビジネスルールの欠如**: アクセシビリティ要件がビジネスルールとして定義されていない
3. **テスト困難性**: アクセシビリティ要件を独立してテストすることが困難

## 決定

**アクセシビリティ要件をドメイン層で定義**し、プレゼンテーション層で実装する。

### 実装アプローチ

1. **ドメイン層でのアクセシビリティ要件定義**: 
   - `AriaLabel` Value Object: ARIAラベルを定義
   - `KeyboardShortcut` Value Object: キーボードショートカットを定義

2. **プレゼンテーション層での実装**: 
   - HTML要素に`aria-label`属性を設定
   - キーボードイベントハンドラーを実装
   - フォーカス管理を実装

3. **一貫性の確保**: ドメイン層で定義されたアクセシビリティ要件を使用することで、一貫性を保つ

### アクセシビリティルール

1. **すべてのUI要素にARIAラベル**: ボタン、入力欄、エラーメッセージなど、すべてのUI要素に適切なARIAラベルを設定
2. **キーボード操作のサポート**: すべての操作をキーボードで実行可能にする
3. **フォーカス管理**: エラー発生時、適切な要素にフォーカスを移動

## 結果

### ポジティブ

- **一貫性**: アクセシビリティ要件がドメイン層で定義され、一貫性が保たれる
- **保守性**: アクセシビリティ要件の変更が容易になる
- **テスト容易性**: アクセシビリティ要件を独立してテストできる
- **コンプライアンス**: WCAG 2.1 Level AA基準への準拠が容易になる

### ネガティブ

- **実装コスト**: ドメイン層に新しいValue Objectが追加される
- **複雑性**: ドメイン層の複雑性が増す（ただし、軽微）

### 検討した代替案

#### 代替案1: アクセシビリティ要件をプレゼンテーション層のみで定義
- **説明**: アクセシビリティ要件をプレゼンテーション層のみで定義
- **Pros**: 実装が簡単、ドメイン層の複雑性を減らせる
- **Cons**: 一貫性が保たれない、ビジネスルールとして定義されない
- **却下理由**: 一貫性と保守性の観点から不適切

#### 代替案2: アクセシビリティ要件をアプリケーション層で定義
- **説明**: アクセシビリティ要件をアプリケーション層で定義
- **Pros**: ドメイン層の複雑性を減らせる
- **Cons**: アクセシビリティ要件が複数のアプリケーションサービスに分散する可能性がある
- **却下理由**: アクセシビリティ要件は横断的関心事であり、ドメイン層で定義する方が適切
