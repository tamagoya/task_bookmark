# ADR-007: スキーマバージョニングとマイグレーション戦略

## ステータス
承認済み

## コンテキスト
Googleカレンダーに保持される情報は数年にわたって資産となります。一方、task-bookmarkは絶えずバージョンアップが考えられます。Googleカレンダー上のデータはリレーショナルDBのように、alterコマンド一つで一斉にデータ更新をすることができません。

そのため、以下の要件を満たす必要があります：
- 今後、Googleカレンダーに保持するデータが増えたり、変更することになっても、後方互換がある形で保持されているデータが読み込める
- データの拡張性を考慮した設計

## 決定
スキーマバージョニングとマイグレーション戦略を採用します：

1. **セマンティックバージョニング**: メジャー.マイナー.パッチ形式を使用
   - メジャーバージョン: 破壊的変更（マイグレーションが必要）
   - マイナーバージョン: 後方互換性のある追加（自動マイグレーション可能）
   - パッチバージョン: バグ修正（互換性に影響なし）

2. **SchemaVersion Value Object**: バージョン管理をドメイン層で実装
   - `isCompatibleWith()`: 互換性判定
   - `canMigrateTo()`: マイグレーション可能性の判定

3. **MetadataMigrator Factory**: マイグレーション戦略の実装
   - `migrate()`: メタデータのマイグレーション
   - `canMigrate()`: マイグレーション可能性の判定
   - `getMigrationPath()`: マイグレーションパスの取得

4. **自動マイグレーション**: 読み込み時に、古いバージョンのデータを自動的に最新バージョンにマイグレーション

5. **拡張フィールド（extensions）**: 将来の拡張のために、未知のフィールドは`extensions`に保持

## 結果

### ポジティブ
- **後方互換性**: 古いバージョンのデータは、新しいバージョンで読み込める
- **前方互換性**: 新しいバージョンのデータは、古いバージョンでも部分的に読み込める（未知のフィールドは`extensions`に保持）
- **長期的な互換性**: 数年にわたって保持されるデータに対応できる
- **データの永続性**: マイグレーション後も、元のデータ構造の情報は保持（監査用）
- **拡張性**: 将来のスキーマ変更に対応できる

### ネガティブ
- **複雑性の増加**: マイグレーションロジックの実装により、コードの複雑性が増加
- **パフォーマンス**: マイグレーション処理により、読み込み時間が延長される可能性
- **テストの複雑性**: 各バージョン間のマイグレーションをテストする必要がある
- **メンテナンス負荷**: 新しいバージョンが追加されるたびに、マイグレーション戦略を実装する必要がある

### 検討した代替案

#### 代替案1: バージョニングなし
- **説明**: スキーマバージョンを管理せず、常に最新の形式のみをサポート
- **却下理由**: 古いデータが読み込めなくなる、長期的な互換性が確保できない

#### 代替案2: 手動マイグレーション
- **説明**: ユーザーが手動でマイグレーションを実行
- **却下理由**: ユーザー体験が悪化、エラーが発生しやすい、Googleカレンダー上のデータを一括更新できない

#### 代替案3: サーバーサイドでのマイグレーション
- **説明**: サーバーサイドでマイグレーションを実行
- **却下理由**: このプロジェクトはChrome拡張機能のみで、サーバーサイドを持たない

#### 代替案4: バージョンごとに別のカレンダーを使用
- **説明**: バージョンごとに別のカレンダーを作成
- **却下理由**: ユーザー体験が悪化、データの分散、管理が複雑になる
