# ADR-031: 無視URL設定の永続化先（chrome.storage.local）

## ステータス
承認済み（2026-05-28）

## コンテキスト
US-10（無視URL設定）で導入する `IgnoreRule` の永続化先を選定する必要がある。

候補:
1. **`chrome.storage.local`**: 端末ローカル、最大 5MB
2. **`chrome.storage.sync`**: 端末間同期、最大 100KB（1アイテム 8KB）
3. **Google Calendar の専用イベント**: クラウド永続化、ユーザーアカウントに紐づく
4. **`IndexedDB`**: 大容量、構造化クエリ可能

ルール想定サイズはルール1件あたり ~256B、上限100件で約 25KB。
ユーザー回答（2026-05-28）により `chrome.storage.local` で開始することが確定済み。

## 決定
**`chrome.storage.local` を採用する。**

ストレージスキーマ:
```json
{
  "ignoreRulesV1": {
    "schemaVersion": 1,
    "rules": [/* IgnoreRule[] */]
  }
}
```

キー名は `ignoreRulesV1` とし、将来のスキーマ変更時は `ignoreRulesV2` 等の新キーへマイグレーションする。

## 代替案
1. **`chrome.storage.sync`（端末間同期）**: 便利だが容量100KB・1アイテム8KBの制約があり、ルール量・将来拡張への余裕が少ない。同期競合のハンドリングも必要になる。**将来検討**として残し、初期は不採用。
2. **Google Calendar の専用イベント**: 既存のCalendar永続化基盤を再利用できる利点はあるが、(a) サイドパネル起動時のCalendar API 呼び出しが必要となりUX体感が劣化する、(b) オフライン時に編集できない、(c) 仕事データとライフサイクルが異なる設定情報を混在させるのは望ましくない、ため不採用。
3. **`IndexedDB`**: 構造化クエリは必要規模ではない（100件程度）。実装コストに対して利得が小さく不採用。

## 結果
### 利点
- 既存の認証情報・復元セッション情報（`lastRestoredEventId` 等）と同じストレージ機構を使用するため、コードベースの一貫性が保たれる
- 容量制限 5MB に対し ~25KB なので余裕は数百倍
- 同期処理の競合・遅延を考慮しなくてよく、CRUD UI のレスポンスを安定させられる（NFR-1.1: 200ms 以内）
- 完全にローカルに留まるため、プライバシーリスクが最小（NFR-2.4）

### 欠点・トレードオフ
- 端末間で設定が同期されない
  - **軽減策**: 必要性が顕在化したタイミングで `chrome.storage.sync` への移行 or デュアル書き込みを検討
- ストレージ破損時にすべてのルールが消失
  - **軽減策**: `schemaVersion` でスキーマ管理、読み込み失敗時は空集合フォールバック（RISK-018）。将来的にエクスポート/インポート機能で対処

### 将来の拡張
- `chrome.storage.sync` への移行を行う場合は ADR を別途作成
- JSON エクスポート/インポート機能を将来追加（フィードバック原文では明示要望なし、ユーザー回答でも初期不要）
