# ADR-024: キャッシュ戦略の選択

## コンテキスト

Unit 6では、パフォーマンス要件を満たすためにキャッシュ機能を実装する必要があります。特に、以下の操作でキャッシュが有効です：

- タブ情報の取得: 頻繁にアクセスされるが、変更頻度は低い
- 保存済み仕事の一覧取得: 過去30日分（最大600件）を3秒以内で取得する必要がある
- 個別のWorkState取得: 同じWorkStateを複数回取得する可能性がある

キャッシュ戦略を実装する際、以下の選択肢があります：

1. **Cache-Aside パターン**: アプリケーションがキャッシュの存在を管理
2. **Write-Through パターン**: データ書き込み時にキャッシュとストレージの両方に書き込む
3. **Write-Behind パターン**: データ書き込みを非同期で実行（ただし、Chrome Extension環境では複雑）
4. **Read-Through パターン**: キャッシュが自動的にストレージからデータを取得

## 決定

**Cache-Aside パターン**を選択します。

具体的には：
- `CacheDecorator`クラスを作成し、既存のサービスメソッドをラップ
- キャッシュキーは`CacheManagementService.getCacheKey()`で生成（操作名とパラメータから一意のキーを生成）
- キャッシュから取得を試み、ヒットしない場合はメインの操作を実行してキャッシュに保存
- TTL（Time To Live）は`CacheStrategy` Value Objectで管理
- エビクションポリシーはLRU（Least Recently Used）をデフォルトとする

## 結果

### ポジティブ

- **シンプルな実装**: Cache-Aside パターンは理解しやすく、実装が簡単
- **柔軟性**: キャッシュの有無をアプリケーション側で制御できる
- **グレースフルデグラデーション**: キャッシュの取得/保存に失敗した場合、メインの操作を実行（可用性を維持）
- **TTL管理**: `CacheStrategy` Value ObjectでTTLを管理し、ドメイン層でビジネスルールを表現
- **メモリ効率**: LRUエビクションポリシーで古いエントリを自動的に削除

### ネガティブ

- **キャッシュミスのオーバーヘッド**: キャッシュミス時は、メインの操作とキャッシュ保存の両方を実行する必要がある
- **一貫性の問題**: キャッシュとストレージの間で一貫性が保証されない（ただし、読み取り専用の操作では問題にならない）
- **メモリ使用量**: キャッシュサイズが大きくなると、メモリ使用量が増加する（50MB以内の要件を満たす必要がある）

### 検討した代替案

- **Write-Through パターン**: データ書き込み時にキャッシュとストレージの両方に書き込む方法。ただし、本拡張機能では読み取り操作が多く、書き込み操作は少ないため、Cache-Aside パターンの方が適している。
- **Write-Behind パターン**: データ書き込みを非同期で実行する方法。ただし、Chrome Extension環境では複雑で、エラーハンドリングが困難。
- **Read-Through パターン**: キャッシュが自動的にストレージからデータを取得する方法。ただし、実装が複雑で、Chrome Extension環境では適していない。
