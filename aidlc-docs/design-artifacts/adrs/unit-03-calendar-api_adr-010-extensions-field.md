# ADR-010: 拡張フィールド（extensions）の設計

## ステータス
承認済み

## コンテキスト
Googleカレンダーに保持される情報は数年にわたって資産となります。一方、task-bookmarkは絶えずバージョンアップが考えられます。Googleカレンダー上のデータはリレーショナルDBのように、alterコマンド一つで一斉にデータ更新をすることができません。

そのため、以下の要件を満たす必要があります：
- 今後、Googleカレンダーに保持するデータが増えたり、変更することになっても、後方互換がある形で保持されているデータが読み込める
- データの拡張性を考慮した設計

## 決定
拡張フィールド（extensions）を採用します：

1. **WorkStateMetadataの拡張**: `extensions?: Record<string, unknown>`フィールドを追加
   - 将来のバージョンで追加される可能性のあるフィールドを格納
   - 任意の構造を持つことができる

2. **TabInfoの拡張**: `extensions?: Record<string, unknown>`フィールドを追加
   - 将来のバージョンで追加される可能性のあるフィールドを格納

3. **前方互換性の実現**: 新しいバージョンで追加されたフィールドは、古いバージョンでは`extensions`に保持される
   - `WorkStateMetadata.createFromRaw()`: 未知のフィールドを`extensions`に格納
   - `EventDescription.tryParse()`: 未知のフィールドを`extensions`に格納

4. **後方互換性の実現**: 古いバージョンのデータは、新しいバージョンで読み込める
   - マイグレーション時に、既存のフィールドは保持される
   - 削除されたフィールドは`extensions`に保持（監査用）

5. **データの保持**: マイグレーション後も、元のデータ構造の情報は`extensions`に保持（監査用）

## 結果

### ポジティブ
- **拡張性**: 将来のスキーマ変更に対応できる
- **前方互換性**: 新しいバージョンのデータは、古いバージョンでも部分的に読み込める
- **後方互換性**: 古いバージョンのデータは、新しいバージョンで読み込める
- **データの永続性**: マイグレーション後も、元のデータ構造の情報は保持（監査用）
- **柔軟性**: 任意の構造を持つことができる

### ネガティブ
- **型安全性の低下**: `extensions`は`Record<string, unknown>`型のため、型安全性が低下
- **検証の複雑性**: `extensions`の内容を検証する必要がある場合、複雑になる
- **ドキュメント化**: `extensions`の内容をドキュメント化する必要がある

### 検討した代替案

#### 代替案1: 拡張フィールドなし
- **説明**: 拡張フィールドを持たず、スキーマ変更時は常にマイグレーションを実行
- **却下理由**: 前方互換性が確保できない、新しいバージョンのデータが古いバージョンで読み込めない

#### 代替案2: 固定スキーマ
- **説明**: スキーマを固定し、変更を許可しない
- **却下理由**: 将来の拡張に対応できない、柔軟性が失われる

#### 代替案3: バージョンごとに別のスキーマ
- **説明**: バージョンごとに完全に別のスキーマを定義
- **却下理由**: マイグレーションが複雑になる、コードの重複

#### 代替案4: 型安全な拡張フィールド
- **説明**: 型安全な拡張フィールドを定義（例: `extensions: { [key: string]: string | number | boolean }`）
- **却下理由**: 柔軟性が失われる、将来の拡張に対応できない
