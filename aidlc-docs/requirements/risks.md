# リスク分析 - タスクブックマーク Chrome 拡張

## 概要
本ドキュメントは、タスクブックマークChrome拡張機能の開発・運用におけるリスクを特定し、軽減策を定義します。リスクは技術的、ビジネス的、運用的、コンプライアンスの観点から分類しています。

---

## リスク評価の基準

### リスクレベル
- **高（High）**: プロジェクトの成功に重大な影響を与える可能性がある
- **中（Medium）**: プロジェクトに影響を与える可能性があるが、軽減策で対処可能
- **低（Low）**: プロジェクトへの影響は限定的

### リスクマトリクス
| 影響度 | 発生確率 | リスクレベル |
|--------|---------|------------|
| 高 | 高 | 高 |
| 高 | 中 | 高 |
| 中 | 高 | 中 |
| 中 | 中 | 中 |
| 低 | 高 | 低 |
| 低 | 中 | 低 |
| 低 | 低 | 低 |

## 1. 技術的リスク

### RISK-001: Google Calendar APIのレート制限
**リスクレベル**: 中  
**カテゴリ**: 技術的リスク

**説明**: 
Google Calendar APIにはレート制限（1秒あたり100リクエスト、1日あたり1,000,000リクエスト）があり、頻繁に保存するユーザー（1日20回程度）が複数いる場合、制限に達する可能性がある。

**影響**: 
- ユーザーが保存操作を実行できない
- エラーメッセージが表示され、UXが低下

**発生確率**: 中（ユーザー数が増加した場合）

**軽減策**: 
1. **リクエストのバッチ処理**: 可能な限り、複数の操作を1つのAPI呼び出しにまとめる
2. **レート制限の監視**: APIレスポンスの`Retry-After`ヘッダーを確認し、適切に待機
3. **エラーハンドリング**: レート制限エラー（429）を検出し、ユーザーに分かりやすいメッセージを表示
4. **リトライ戦略**: 指数バックオフを使用したリトライ機能を実装
5. **ローカルキャッシュ**: 保存済み仕事の一覧をローカルにキャッシュし、API呼び出しを削減

**監視**: 
- API呼び出し回数をログに記録
- レート制限エラーの発生頻度を監視

### RISK-002: OAuth認証フローの複雑性とトークン管理
**リスクレベル**: 高  
**カテゴリ**: 技術的リスク

**説明**: 
OAuth 2.0認証の実装が複雑で、トークンの有効期限管理、リフレッシュトークンの処理、エラーハンドリングが適切でない場合、ユーザーが認証できなくなる。

**影響**: 
- ユーザーが拡張機能を使用できない
- 認証エラーが頻発し、UXが大幅に低下

**発生確率**: 中（実装の複雑さによる）

**軽減策**: 
1. **Chrome Identity APIの活用**: Chrome拡張機能専用の`chrome.identity` APIを使用し、OAuthフローを簡素化
2. **段階的な実装**: まず認証機能のみを実装し、十分にテストしてから他の機能を追加
3. **トークンの自動更新**: トークンの有効期限を監視し、期限切れ前に自動的に更新
4. **エラーハンドリング**: 認証エラーの種類に応じて、適切なメッセージと再認証フローを提供
5. **テスト**: 認証フローの包括的なテスト（正常系、異常系）を実施

**監視**: 
- 認証エラーの発生頻度を監視
- トークン更新の成功率を監視

### RISK-003: Manifest V3の制約と移行の複雑性
**リスクレベル**: 中  
**カテゴリ**: 技術的リスク

**説明**: 
Manifest V3では、Service Workerベースのバックグラウンド処理、Dynamic Content Scriptsの制限、CSPの強化など、従来のManifest V2とは異なる制約がある。

**影響**: 
- 実装が予想以上に複雑になる
- 機能の制限により、UXが低下する可能性

**発生確率**: 中（Manifest V3の学習曲線による）

**軽減策**: 
1. **早期プロトタイプ**: Manifest V3の主要機能（Service Worker、Side Panel API）を早期にプロトタイプし、技術検証
2. **公式ドキュメントの参照**: Chrome拡張機能の公式ドキュメントとベストプラクティスを参照
3. **段階的な実装**: まず最小限の機能でManifest V3に準拠し、徐々に機能を追加
4. **コミュニティリソース**: Manifest V3への移行事例やコミュニティの知見を活用

**監視**: 
- Manifest V3の制約による機能制限を記録
- 代替実装方法の検討

### RISK-004: 大量のタブ復元時のパフォーマンス問題
**リスクレベル**: 中  
**カテゴリ**: 技術的リスク

**説明**: 
ユーザーが20個以上のタブを復元する場合、ブラウザのパフォーマンスが低下し、フリーズする可能性がある。

**影響**: 
- ブラウザが応答しなくなる
- ユーザーの作業が中断される
- UXが大幅に低下

**発生確率**: 中（平均10タブだが、最大20タブ以上の場合がある）

**軽減策**: 
1. **段階的なタブ読み込み**: タブを一度に開かず、数個ずつ段階的に開く
2. **最大タブ数の制限**: 復元時の最大タブ数を設定（例: 30個）し、それを超える場合は警告を表示
3. **遅延読み込み**: タブを開いた後、実際のページ読み込みを遅延させる（`chrome.tabs.update`の`url`を後から設定）
4. **プログレスインジケーター**: 復元中はプログレスバーを表示し、ユーザーに進行状況を伝える
5. **パフォーマンステスト**: 大量のタブ（20個、50個）での復元テストを実施

**監視**: 
- 復元にかかる時間をログに記録
- ユーザーからのパフォーマンスに関するフィードバックを収集

### RISK-014: 全ウィンドウ保存・保存後全タブ閉じに伴うリスク
**リスクレベル**: 中  
**カテゴリ**: 技術的リスク・ビジネスリスク

**説明**: 
保存対象を「すべてのChromeウィンドウのタブ」とし、保存後に全タブを閉じて新規ウィンドウを表示する仕様により、以下のリスクがある。(1) 複数ウィンドウ分のタブ数が増え、取得・保存のレスポンス時間やAPI負荷が増加する。(2) 保存実行により意図せず全ウィンドウのタブが閉じられ、ユーザーが「保存したつもりがない」と感じる誤操作リスクがある。

**影響**: 
- パフォーマンス低下（全ウィンドウのタブ取得が1秒を超える場合）
- ユーザーが「全タブが閉じられる」ことに驚き、不安を感じる可能性
- 保存失敗時にタブは閉じない設計とするが、実装の不備で誤って閉じる可能性

**発生確率**: 中

**軽減策**: 
1. **パフォーマンス**: 全ウィンドウのタブ取得を1秒以内とするNFRを設定し、必要に応じてキャッシュや段階表示を検討
2. **UX**: サイドパネルやヘルプで「保存するとすべてのウィンドウのタブが保存され、保存後にそれらのタブは閉じられ、新しいウィンドウが開きます」と明示する
3. **実装**: 保存が成功した場合にのみ、保存対象のタブIDを閉じ、続けて新規ウィンドウを作成する。保存失敗時はタブを閉じず新規ウィンドウも開かない
4. **テスト**: 保存成功時のみタブ閉じ・新規ウィンドウ作成が行われることをテストで保証する

**監視**: 
- 全ウィンドウタブ取得時間のログ
- ユーザーフィードバック（「意図せずタブが閉じられた」等）

### RISK-015: Google CalendarのDOM変更による復元ボタン表示不具合
**リスクレベル**: 中  
**カテゴリ**: 技術的リスク

**説明**: 
Google Calendarの予定詳細に「復元」ボタンをContent Scriptで注入しているため、GoogleがカレンダーUIのDOM構造を変更すると、ボタンの表示位置や表示自体が動作しなくなる可能性がある。

**影響**: 
- カレンダー上からの復元が利用できなくなる（サイドパネルからの復元は継続して利用可能）
- ユーザーがカレンダー上で復元できないと感じる

**発生確率**: 中（GoogleのUI更新は定期的に発生する）

**軽減策**:
1. **セレクタの保守**: 予定詳細のセレクタを定数化し、複数の候補セレクタをフォールバックとして試す
2. **機能の独立性**: 復元の主導線はサイドパネルであり、カレンダー上のボタンは追加の導線として位置づける
3. **バージョン確認**: 定期的にGoogle Calendarの表示を確認し、DOM変更時はセレクタを更新する
4. **「前のタスクへ」**: イベント詳細URL（eventedit）はGoogleの非公式仕様に依存するため、URL構築を一箇所に集約し、将来の仕様変更時に修正しやすくする

**監視**: 
- カレンダー上での復元ボタン表示・動作の手動確認をリリース前チェックに含める

### RISK-005: Chrome拡張機能APIの変更や非推奨化
**リスクレベル**: 低  
**カテゴリ**: 技術的リスク

**説明**: 
Chrome拡張機能のAPIが変更されたり、非推奨化されたりする可能性がある。特に、Side Panel APIは比較的新しいAPIのため、将来の変更の影響を受ける可能性がある。

**影響**: 
- 既存の機能が動作しなくなる
- コードの修正が必要になる

**発生確率**: 低（Chromeは後方互換性を重視）

**軽減策**: 
1. **公式ドキュメントの監視**: Chrome拡張機能の公式ブログやドキュメントを定期的に確認
2. **バージョン固定**: 使用するAPIのバージョンを固定し、変更時は慎重にテスト
3. **フォールバック実装**: Side Panel APIが利用できない場合、popup.htmlへのフォールバックを実装

**監視**: 
- Chrome拡張機能のリリースノートを定期的に確認

## 2. セキュリティリスク

### RISK-006: 機密情報を含むURLの保存
**リスクレベル**: 高  
**カテゴリ**: セキュリティリスク

**説明**: 
URLに認証トークン、セッションID、個人情報などの機密情報が含まれる可能性がある。これらがGoogle Calendarに保存されると、セキュリティリスクとなる。

**影響**: 
- 機密情報の漏洩
- 不正アクセスのリスク
- コンプライアンス違反

**発生確率**: 中（多くのWebアプリケーションでURLにトークンを含む）

**軽減策**: 
1. **ユーザーへの警告**: 保存時に、機密情報が含まれる可能性があることを警告
2. **URL編集機能**: 保存後にURLを編集・削除できる機能を提供（User Story 6）
3. **URLの検証**: URLに機密情報のパターン（`token=`, `session=`, `auth=`など）が含まれていないか検証し、警告を表示（オプション）
4. **プライバシーポリシー**: プライバシーポリシーで、ユーザーが機密情報を含むURLを保存しないよう明記

**監視**: 
- ユーザーからのセキュリティに関するフィードバックを収集

---

### RISK-007: OAuthトークンの漏洩
**リスクレベル**: 高  
**カテゴリ**: セキュリティリスク

**説明**: 
OAuthトークンがChrome Storageに保存される際、適切に保護されていない場合、悪意のある拡張機能やスクリプトにアクセスされる可能性がある。

**影響**: 
- ユーザーのGoogleアカウントへの不正アクセス
- カレンダーデータの改ざん・削除

**発生確率**: 低（Chrome Storage APIは比較的安全）

**軽減策**: 
1. **Chrome Storage APIの使用**: `chrome.storage.local`を使用し、Chromeのセキュリティ機能を活用
2. **最小限のスコープ**: 必要最小限のAPIスコープ（`https://www.googleapis.com/auth/calendar`）のみを要求
3. **トークンの暗号化**: 可能な限り、トークンを暗号化して保存（Chrome Storage APIの機能を利用）
4. **トークンのライフタイム管理**: トークンの有効期限を適切に管理し、不要になったトークンは削除
5. **セキュリティ監査**: 定期的にセキュリティ監査を実施

**監視**: 
- トークンアクセスのログを記録（開発環境のみ）
- セキュリティ脆弱性の定期的な確認

---

### RISK-008: XSS（Cross-Site Scripting）攻撃
**リスクレベル**: 中  
**カテゴリ**: セキュリティリスク

**説明**: 
サイドパネルやポップアップのUIで、ユーザー入力（仕事名、メモ）を適切にサニタイズしない場合、XSS攻撃のリスクがある。

**影響**: 
- 悪意のあるスクリプトの実行
- ユーザーデータの窃取

**発生確率**: 低（適切な実装により回避可能）

**軽減策**: 
1. **入力のサニタイズ**: すべてのユーザー入力（仕事名、メモ）をサニタイズ
2. **CSPの適用**: Content Security Policyを適切に設定し、インラインスクリプトを禁止
3. **フレームワークの使用**: ReactやVueなどのフレームワークを使用し、自動的にXSSを防止
4. **セキュリティテスト**: XSS脆弱性のテストを実施

**監視**: 
- セキュリティ監査ツール（OWASP ZAPなど）を使用した定期的なテスト

## 3. ビジネスリスク

### RISK-009: ユーザー採用率の低下
**リスクレベル**: 中  
**カテゴリ**: ビジネスリスク

**説明**: 
拡張機能のUXが複雑で、ユーザーが「ブックマーク作成と同等の手軽さ」を感じられない場合、採用率が低下する。

**影響**: 
- プロジェクトの成功指標（タスク切り替え時の生産性向上）が達成できない
- ユーザーが拡張機能をアンインストール

**発生確率**: 中（UX設計の難しさによる）

**軽減策**: 
1. **ユーザーテスト**: 早期にプロトタイプを作成し、ユーザーテストを実施
2. **段階的な機能公開**: MVPで最小限の機能を提供し、ユーザーフィードバックを収集
3. **UI/UXの改善**: ユーザーフィードバックに基づき、UI/UXを継続的に改善
4. **オンボーディング**: 初回利用時のチュートリアルやヘルプを提供

**監視**: 
- ユーザーフィードバックの収集
- アンインストール率の監視

**カテゴリ**: ビジネスリスク

**説明**: 
Google Calendar APIの仕様が変更されたり、非推奨化されたりする可能性がある。

**影響**: 
- 既存の機能が動作しなくなる
- コードの修正が必要になる

**発生確率**: 低（Googleは後方互換性を重視）

**軽減策**:

3. **代替案の検討**: 他のカレンダーサービス（Outlook、Apple Calendar）への対応を検討（将来の拡張）

**監視**: 
- Google Calendar APIのリリースノートを定期的に確認

## 4. 運用リスク

### RISK-011: エラーログの不足によるデバッグの困難
**リスクレベル**: 中  
**カテゴリ**: 運用リスク

**説明**: 
本番環境でエラーが発生した際、適切なログが記録されていない場合、原因の特定が困難になる。

**影響**: 
- バグの修正に時間がかかる
- ユーザーへの影響が長引く

**発生確率**: 中（ログ設計の不備による）

**軽減策**: 
1. **包括的なログ**: すべてのエラー、主要な操作（保存、復元）をログに記録
2. **構造化ログ**: JSON形式の構造化ログを使用し、検索・分析を容易にする
3. **ログレベルの設定**: 開発環境と本番環境でログレベルを適切に設定
4. **プライバシー配慮**: 個人情報（URL、タイトル）を含むログは記録しない

**監視**: 
- エラーログの定期的な確認
- エラー発生率の監視

**リスクレベル**: 低  
**カテゴリ**: 運用リスク

**説明**: 
Chrome Web Storeの審査基準を満たさない場合、拡張機能が公開されない。

**影響**: 
- リリースの遅延
- 追加の修正作業が必要

**発生確率**: 低（審査基準を遵守すれば問題ない）

**軽減策**: 
1. **審査基準の確認**: Chrome Web Storeの審査基準を事前に確認し、準拠
2. **プライバシーポリシー**: プライバシーポリシーを公開
3. **利用規約**: 利用規約を明確に定義
4. **テスト**: 審査前に十分なテストを実施

**監視**: 
- Chrome Web Storeの審査結果を確認

## 5. コンプライアンスリスク

### RISK-013: データ保護法（GDPR）への非準拠
**リスクレベル**: 中  
**カテゴリ**: コンプライアンスリスク

**説明**: 
ユーザーデータ（URL、タイトルなど）の取り扱いが、GDPRなどのデータ保護法に準拠していない場合、法的リスクがある。

**影響**: 
- 法的責任
- ユーザーの信頼低下

**発生確率**: 低（適切な実装により回避可能）

**軽減策**: 
1. **プライバシーポリシー**: データの取り扱いについて、明確なプライバシーポリシーを公開
2. **データの最小化**: 必要最小限のデータのみを収集
3. **ユーザーの同意**: データの取り扱いについて、ユーザーの同意を得る
4. **データの削除**: ユーザーがデータを削除できる機能を提供（Google Calendarから手動削除）

**監視**: 
- データ保護法の変更を定期的に確認

## リスク管理プロセス

### リスクの監視
- 定期的なリスクレビュー（月1回）
- 新しいリスクの特定
- 既存リスクの再評価

### リスクの軽減
- 各リスクに対して、軽減策を実装
- 軽減策の効果を測定
- 必要に応じて、追加の軽減策を検討

### リスクのエスカレーション
- 高リスクの場合は、プロジェクトマネージャーに報告
- リスクが実現した場合、即座に対応
